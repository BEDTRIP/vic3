# Методология документации

Общие правила документации для любого проекта, где документы ведут вместе человек и агенты. Каждый проект — своё
пространство: свои правила работы, навыки, инструменты, точка входа агента; метод их не касается — он только о том,
как вести документацию и работу, чтобы в любом проекте и в нескольких сразу можно было ориентироваться одинаково.

Метод стоит на общепринятом: виды документов — по Diátaxis, работа — как в трекерах (roadmap, epic, issue), выборы —
ADR, аварии — postmortem. Названия русские, стандартное — в скобках; статусы и ключи шапок — стандартные значения:
агент знает их заранее и не учит свои.

Метод один и цельный: в проекте он лежит целиком, без своих вариантов правил, — папка `docs/methodology/`, у всех
заметок `project: methodology`. Где метод не подходит, правят сам метод — для всех проектов сразу, а не исключением
в документах проекта: два места на одно правило расходятся. Чем работа в проекте отличается — в его
[[План проекта (roadmap)|плане]] и правилах агента. Как завести метод в проект и как взять его обновление —
[[Перевод проекта на методологию (migration guide)]].

Строка у понятия — само правило: этой карты хватает, чтобы работать по методу; заметка — подробности и «почему».

## Основа

- [[Один вопрос — одно место (single source of truth)]] — единый источник правды: у каждого вопроса один документ, вид — `type`: вход,
  понятие (explanation), карта (MOC), документ кода, процедура (how-to), справочник (reference), план (roadmap), этап
  (epic), задача (issue), ADR, урок, история.
- [[Где лежит (docs layout)]] — всё в `docs/`; план, этапы и задачи — в `план/`; в каждой папке `README.md` — файл папки (у
  однотипных — таблица Bases по шапкам); списки руками не ведут; таблица — под ширину заметки, копией образца:
  четыре колонки, имя первой, `description` последней, высокие строки; правила агента, данные и фикстуры — не документы.
- [[Проект из нескольких репо (polyrepo)]] — узел над репо: план, этапы, задачи, сквозное, метод; документ — в репо
  того, что описывает; ключи и номера ADR уникальны по проекту; ссылки между репо проверяет узел.
- [[Шапка документа (frontmatter)]] — у каждого `type`, `description` (одна строка: о чём и когда открывать),
  `project`, `tags`; ключи и статусы своего вида — стандартные; служебные (`paths`, `verified`, `generated`) — когда
  по ним что-то делается; даты — в `date`.
- [[Ссылки (wikilinks)]] — упомянул документ — ссылка Obsidian, на то место, о котором речь (раздел, `^метка`, вставка); на код —
  путь в `` ` ` ``; одно имя у двух документов — хвост пути; переименование — в Obsidian, одним коммитом.
- [[Как писать (style guide)]] — каждое утверждение проверено или «не выяснено»; по памяти — с пометкой до сверки; источник — с
  тем, как прочитан; документ — в том же коммите, что код; почему, а не только как; выжимка и адрес; рекомендация
  первой (BLUF); номера и ключи постоянные; счётчики — только где считает машина; в коде — только актуальное.

## Что есть

- [[Понятие (explanation)]] — explanation и спецификация: одна заметка на понятие — «Суть», «Как должно быть», «Где», «Открыто»;
  синонимы — в `aliases`; задача начинается с «Как должно быть» понятия; карта (MOC) — группы понятий по смыслу,
  каждое понятие есть на карте.
- [[Внешний источник (vendoring)]] — чужое, на чём стоит проект, — снимок и граф документов врозь; справочник «как
  сделано», `verified` — коммит снимка; своё поверх чужого — у себя с `uses` / `replaces`; дефект чужого — баг в его
  графе.
- [[Документ кода (module README)]] — рядом с кодом: модули, входы, данные, как запустить и проверить; `paths`; код
  ссылается только на него, ключи задач и номера ADR; не в папке, которую программа перебирает целиком; у продукта,
  который программа берёт папками (мод игры), — по подсистемам в `docs/код/`.
- [[Процедура и справочник (how-to, reference)]] — how-to: как сделать руками (команды, порядок, грабли); reference: где посмотреть
  значение (таблицы, часто собранные скриптом); без истории, «что это» — ссылкой на понятие.
- [[Окружение (infrastructure)]] — устройство: понятие, процедура, справочник, `devices`; `verified` — сверка с устройством; секретов
  нет.

## Что делаем

- [[План проекта (roadmap)]] — `план/README.md` — «Состояние» до пяти строк (идёт, следующее, горит, ждёт человека),
  цели и принципы, обзор открытых этапов с их задачами, отличия проекта; только открытое; ревизия раз в месяц
  (backlog refinement).
- [[Этап (epic)]] — короткий файл `план/<имя>` с начала — цель, открытые вопросы, порядок, Definition of Done; работа —
  в задачах, хода в этапе нет; файл этапа — обзор для человека: задачи видами «Открытые» (по `status`) и «Архив»,
  «порядок» агент держит по факту; направление без конца — тоже этап; статусы `todo` / `in-progress` / `on-hold` /
  `done`; на потом — тема этапом `on-hold`, отдельная задача — в этап «Когда-нибудь», срок — `start`.
- [[Задача (issue)]] — файл `план/задачи/<ключ> — <тема>` с ключом области (`NET-13`), `kind: task` или `bug`;
  `assignee`, `status`, `touches`, `depends`; критерии приёмки — «Проверка»; ход — одна–три строки на заход с
  ошибками агента; статусы `todo` → `in-progress` → `review` (сделано, в `question` — что посмотреть) → `done`
  (принято в деле), `blocked` с `question`, `wontdo`; ответ человека — в `answer`, задача с ним — можно делать,
  сессия в этапе начинает с них; выбор человека — варианты с номерами в задаче, она `blocked`; взять — коммит
  файла в общую ветку; коммит — с ключом в начале; уходишь — передача (handoff) в ходе; закрытая — в историю.
- [[Очередь человека (review queue)]] — всё, что ждёт человека, видом по шапкам: задачи `review` и `blocked` на нём,
  баги `fixed`; приёмка — обзором этапа: сессия ведёт по `question`, человек отвечает в `answer` «принято» или «вернуть»;
  WIP-лимит — очередь растёт, новое не начинают.
- [[Несколько агентов (multi-agent)]] — без оркестратора: нарезка заранее, заявка на задачу, своя рабочая копия и ветка,
  параллельно — только непересекающиеся `touches`, в общую ветку агент сливает сам при `review`, после проверки;
  коммит — явными путями; главная сессия — когда нарезать заранее нельзя.
- [[Закрытие этапа (epic closure)]] — каждая задача закрыта или перенесена, Definition of Done проверен, понятия по факту, правила из
  ADR этапа — в понятиях, ретроспектива — ошибки агента уроками, файл — в историю с «Итогом»; наполовину не
  закрывать.
- [[Задание агенту (agent brief)]] — работа агенту без человека (`/loop` или разовое): задача с порядком задач, границами и стопом;
  подготовка с человеком, работа — в чистой сессии; вопросов нет — задача `blocked` и следующая.
- [[Ночная работа (multi-agent night run)]] — без человека на нескольких аккаунтах: дирижёр в `/loop` раздаёт задачи
  плана исполнителям и проверяет итог по файлам, сам не делает; исполнитель — одна задача по методу в своей копии,
  `ИТОГ:` последней строкой; всё, на что днём нужно согласие, ночью отклоняет хук; аккаунт — по окну лимита и его
  сбросу, запас дирижёру; модель по работе; аккаунты и число исполнителей — настройка проекта.

## Почему, что сломано, чему научились

- [[Решение (ADR)]] — запись выбора человека — «Контекст», «Решили», «Последствия»; только текущее, варианты — в
  задаче, где выбирали; `ADR-0012`, номер постоянный; не норма — правило из него пишут в понятие; принятый не
  переписывают; `accepted`, заменённый — `superseded`, отменённый — `deprecated`; файл — когда выбирали между
  вариантами, а не на каждое «да».
- [[Баг (bug)]] — задача `kind: bug`, дефект, который не чинишь сейчас, — файл сразу, без вопроса, с
  воспроизведением и `severity`; цикл Bugzilla: `unconfirmed` → `confirmed` → `fixed` (ждёт выкладки) → `verified`,
  итог `wontfix` / `invalid` / `duplicate`; авария — тот же баг с postmortem: влияние, хронология, причина, действия,
  уроки.
- [[Урок (lessons learned)]] — опыт, который пригодится вне своего места; файл на вывод, заголовок — вывод, `applies` —
  где ещё пригодится; на месте действия правило остаётся строкой со ссылкой на урок; нарушен повторно — ему
  исполнитель.

## Как было и инструменты

- [[История (archive)]] — закрытое целиком — этапы, задачи, заменённые ADR, снимки, исследования; «Итог» сверху; читать
  только по ссылке; текст не переписывают, ссылки на переехавшее — чинят.
- [[Проверка (docs lint)]] — скрипт проекта после правки документов — ссылки, якоря, шапки, карта, упоминания
  текстом, `paths`, `verified`, ссылки из кода, задачи и заявки, размер рабочих файлов; у правила, нарушение которого
  дорого, — исполнитель (проверка, CI, хук), а не абзац.
- [[Скрипт проверки (linter)]] — как его написать под проект; образец ядра.
- [[Перевод проекта на методологию (migration guide)]] — по порядку: метод и хук начала сессии, понятия и карта (показать человеку),
  процедуры, план, ADR, баги, шапки, история; обновление метода — папку заменить целиком, по диффу привести документы
  проекта.
